IPPON.LV — диагностика рейтингов и исправления, 29.10.2026

1. ПОДТВЕРЖДЁННЫЕ ПРОБЛЕМНЫЕ ЗАПИСИ
В публичном API /api/rezultati/admin/sources категория reitingi содержит:
ippon_text, area_id=115 — Sporta kluba "IPPON.LV" sportistu reitings. Sezona 2020-2022
ippon_text, area_id=116 — Sporta kluba "IPPON.LV" sportistu reitings. Sezona 2022-2023
ippon_text, area_id=117 — Sporta kluba "IPPON.LV" sportistu reitings. Sezona 2023-2024

Это не соревнования ippon_sorevnovanija с номерами 115/116/117:
те номера относятся к Grand Prix Jurmala 2017, K-Riga 2017,
Salaspils Kauss 2017. Соревнования не переименованы и не изменены.

У трёх рейтингов поле name пустое, поэтому админка показывала #ID.
Название сезона сохранилось внутри первой строки HTML-таблицы.
Пустые name подтверждены также в имеющейся резервной копии базы.
Дата 2024-07-23 получается из c_time исходной записи; это дата создания
материала, а не сезон рейтинга. Дата не исправлялась и не подменялась.

Публичный API отдавал этим рейтингам record_type=sacensibas,
layout_type=competition_default и structured_data={rows:[]}, хотя
custom_html содержал таблицу. В результате рейтинг выпадал из фильтра
Reitingi, а макет соревнований показывал пустые структурированные строки
и игнорировал существующий HTML. Ошибочный slug также мог открывать
соревнование с совпадающим числовым ID.

2. ПРИЧИНЫ В КОДЕ
admin/index.html, saveSourceOverride(): ветка учитывала только eksamens;
любой другой тип, включая reitings, сохранялся как sacensibas.
При сохранении HTML приоритет имело скрытое rezSourceCustomHtml,
а не актуальное поле rezManualCustomHtml, куда добавлялась импортированная
таблица. Поэтому обновлённый предпросмотр не гарантировал сохранения.
При открытии источника редактор строк соревнований также перезаписывал
скрытые structured_data рейтинга; это отключено для иных типов.
Дополнительно исправлены подтверждённые дефекты импорта:
- CSV одновременно делился по запятой и точке с запятой: 12,5 превращалось
  в две ячейки; перенос внутри кавычек разделял одну запись на две.
- escapeHtml терял числовой ноль.
- пропуски в массиве ячеек Excel приводили к сдвигу последующих столбцов.
- завершившийся асинхронный импорт мог попасть в другой открытый материал.

В ensureRezultatiSchema также удалено принудительное присваивание
sacensibas уже валидным типам eksamens/reitings. Этот участок не был
причиной повреждённых overrides трёх записей ippon_text, но представлял
риск для корректно типизированных записей в ippon_sorevnovanija.

4. ИСПРАВЛЕНИЯ И ФАЙЛЫ
server.js
  В ответах API восстанавливается представление ошибочно сохранённого
  рейтинга только при явном заголовке сезонного рейтинга в исходном HTML,
  макете соревнования и отсутствии строк соревнований. Существующий
  custom_html остаётся источником отображения; исходный HTML не заменяется.
  При пустом name отображаемое название берётся из существующего заголовка.
  Старые ошибочные ссылки сопоставляются с источником ippon_text, а не
  соревнованием того же номера. Валидные типы больше не сбрасываются
  при запуске сервера.
scripts/rating-source.js
  Условия восстановления представления и извлечение имеющегося заголовка.
admin/index.html
  Исправлены сохранение типа/HTML, сохранность структурированных данных,
  импорт без замены старого содержимого, защита при смене редактируемой
  записи, нули и пустые столбцы Excel.
assets/table-import.js
  Разбор CSV с одним разделителем, BOM, кавычками и многострочными ячейками;
  повреждённый CSV отклоняется до изменения содержимого редактора.
rezultati.html
  Поддержка прежних ошибочных URL и сохранение нуля при экранировании.
rezultati-single.html
  Рейтинг со старой ссылки перенаправляется на свою страницу в rezultati.html,
  а не блокируется сообщением «страница только для соревнований».
  Нули и экранированные переносы HTML обрабатываются корректно.
scripts/ratings.test.js
  Регрессионные тесты безопасного восстановления представления и CSV.

База данных автоматически не исправляется и не мигрируется. Названия,
даты, результаты, позиции, исходные HTML и типы записей в рабочей БД
не переписывались. Изменения источников выполнялись ТОЛЬКО в отдельной
тестовой копии .tmp-ratings/test.db. Чтением проверено совпадение
диагностированных исходных записей рабочей БД до и после работы.
При будущем явном сохранении пользователем админка запишет корректный
тип рейтинга и актуальный HTML обычным механизмом сохранения.
