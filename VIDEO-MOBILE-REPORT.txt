ПРИЧИНА
Публичный /uploads/ игнорирует HTTP Range. Все 6 действующих MP4 на
www.ippon.lv при Range: bytes=0-1023 вернули 200, video/mp4, chunked,
полный файл, без Accept-Ranges и Content-Range. Это воспроизведено и
объясняется обработчиком /uploads/ в server.js: fs.readFile + HTTP 200.
Nginx присутствует в публичном ответе; его конфигурации в репозитории нет,
доступ к действующей конфигурации сервера не предоставлен.
На основном домене ippon.lv есть 301 на www.ippon.lv; прямые URL видео
на www возвращают 200 без 403/404/redirect. Видео same-origin, CORS не нужен.

ИЗМЕНЕНИЯ
server.js: только MP4/WebM в /uploads/ направляются в потоковый обработчик.
scripts/serve-video.js: GET/HEAD, 200/206/416/404/405, Content-Length,
Content-Range, Accept-Ranges, одиночные, открытые и суффиксные диапазоны;
освобождение потока при разрыве соединения, обработка ошибки чтения.
Неподдерживаемые/multiple Range игнорируются с обычным 200; If-Range
с несовпадающим Last-Modified приводит к полному ответу.
treneris-single.html: video.load() после динамического изменения source.
scripts/serve-video.test.js: воспроизводимый HTTP-регрессионный тест.
treneri.html, CSS, дизайн и положение секции не изменены.

UPLOAD
Админка использует /api/upload-video с binary body и X-Upload-* заголовками.
Видео хранятся локально в uploads/trainers/<id>/video, не в Spaces.
Сохраняемая relativeUrl соответствует локальному файлу; MIME берётся
из проверенного типа контейнера, расширение проверяется по сигнатуре.
api/upload.php не участвует в этом пути загрузки видео.
Нормализация не добавлена: все имеющиеся файлы уже совместимы.
Ограничение: upload проверяет контейнер, но не проверяет кодеки внутри
будущих MP4/WebM. Для будущих загрузок использовать H.264/AAC-LC MP4.

ДЕПЛОЙ (НЕ ВЫПОЛНЕН)
mobile-video.patch содержит только 4 файла исправления и теста, без БД,
uploads, .env, скачанных видео и диагностических инструментов.
SSH-адрес, каталог приложения и имя процесса/сервиса не установлены.
Ниже точные операции, но переменные требуется заполнить реальными
параметрами; не следует угадывать имя сервиса или выполнять оба рестарта.

На локальном PowerShell после получения параметров:
  $IpponSsh = 'USER@HOST'
  scp ./mobile-video.patch "${IpponSsh}:~/mobile-video.patch"
  ssh $IpponSsh

На Linux-сервере (каталог должен быть действующим checkout IPPON):
  set -eu
  IPPON_APP_DIR='/ACTUAL/APP/DIRECTORY'
  cd "$IPPON_APP_DIR"
  git status --short
  git apply --stat "$HOME/mobile-video.patch"
  git apply --check "$HOME/mobile-video.patch"
  backup_dir="$HOME/ippon-video-backup-$(date +%Y%m%d-%H%M%S)"
  mkdir -p "$backup_dir"
  cp -p server.js treneris-single.html "$backup_dir/"
  git apply "$HOME/mobile-video.patch"
  node --check server.js
  node --check scripts/serve-video.js
  node --test scripts/serve-video.test.js

Если git apply --check сообщает конфликт — остановиться, не применять
с --reject/--force. Сначала сопоставить отличия действующего checkout.
Если проверка после применения не проходит — не перезапускать процесс.

Только подтверждённый вариант управления процессом:
  pm2 restart ACTUAL_PROCESS_NAME
ИЛИ
  sudo systemctl restart ACTUAL_SERVICE_NAME

Проверить публичную выдачу после перезапуска:
  VIDEO_URL='https://www.ippon.lv/uploads/trainers/2/video/copy_2df16e37-28fa-46c5-ad8c-d2c6258097a5.mp4'
  curl -fSI "$VIDEO_URL"
  curl -fSs -D - -H 'Range: bytes=0-1023' "$VIDEO_URL" -o /tmp/ippon-video-range.bin
  wc -c /tmp/ippon-video-range.bin
Ожидается 206, Content-Range bytes 0-1023/10813120 и 1024 байта.
Если публично всё ещё 200, проверить Nginx location /uploads/ и
передачу Range/If-Range к Node. Не добавлять второй обработчик Range
или конфигурацию Nginx вслепую. Действующая конфигурация не изучена.

Откат кода при необходимости (до любых дальнейших изменений):
  git apply --reverse --check "$HOME/mobile-video.patch"
  git apply --reverse "$HOME/mobile-video.patch"
  # Затем тот же подтверждённый restart процесса.
Эти операции не затрагивают БД и существующие видео.

ПРОВЕРКА БУДУЩЕГО ФАЙЛА (на сервере с установленным ffprobe)
  ffprobe -v error -show_entries stream=codec_name,profile,pix_fmt,width,height,level -of json input.mp4
Если будущий файл несовместим, отдельная копия без перезаписи оригинала:
  ffmpeg -n -i input.mp4 -map 0:v:0 -map '0:a:0?' -c:v libx264 -pix_fmt yuv420p -crf 22 -preset medium -c:a aac -profile:a aac_low -b:a 128k -movflags +faststart output-compatible.mp4
Проверить выход ffprobe и воспроизведение до загрузки нового файла.
Не применять массово; для нынешних шести файлов это не требуется.
